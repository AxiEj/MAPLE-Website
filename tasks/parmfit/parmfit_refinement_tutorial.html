Refinement Tutorial

Overview

This tutorial walks through the Refinement route of parmfit(method=refinement) in four runs on o-iodophenol (choi001), a FreeSolv hydration-benchmark solute, supplied as the GAFF2 (General AMBER Force Field)-typed choi001_gaff2.mol2, already assigned abcg2 charges by antechamber. Case 1 refines bonded terms and torsions with every default; Case 2 derives RESP (restrained electrostatic potential) charges and adds a Gaussian reference; Case 3 walks the TorsionFit QM (quantum-mechanical) modes 2 and 3 (Refine3, Refine4). The iodine also raises one detail that light molecules never encounter: Gaussian's built-in Merz–Kollman radius table has no fifth-row entries, and you will see exactly how ParmFit supplies them. Every excerpt below is taken from verified runs of the inputs shown here (Refine1–4.inp plus their sidecar configs).

Every run writes a <base>.parmfitrun.in file next to the output that echoes your configuration with defaults filled in; use it to confirm the keys ParmFit actually read, and watch the log for Unknown left-hand warnings, which flag keys that no builder consumed. The reference definition of every key lives in the Refinement manual page and the shared sections of the ParmFit hub; software and input requirements are summarized in the hub's Requirements section.

Example Files

A linked file name on this page opens the original file from the verified runs, hosted in the MAPLE-Tutorial repository; every input and output file is linked where it is used in the cases below. Save the input files of one case into one folder; Case 1 starts from Refine1.inp.

Software. Every case needs AmberTools on PATH. Case 1 needs nothing else; Cases 2 and 3 also need Gaussian 16, which evaluates the ESP for the RESP charges and runs the QM reference — see the hub's Requirements and QM Reference sections.

The complete run archive, including every _work/ directory, is on Zenodo: 10.5281/zenodo.23126271. It has one zip per case — Case1.zip (30 KB), Case2.zip (62 MB), and Case3.zip (1.7 GB; Refine3 and Refine4) — and each unpacks to a folder of the same name. The NCAA and MetalAA archives use the same zip names, so keep each tutorial in its own folder. To rerun a case, start from its input files in a new folder: inside an unpacked archive folder, TorsionFit would read the archived scans instead of running its own scan (see the hub’s Scan Reuse).

Case 1 — The basic input: bonded refinement

Goal. Refine the bonded terms and torsions of a small molecule provided as a GAFF2-typed mol2, keeping its original charges. This is entirely default behavior: chg_fit=none, bonded=mseminario, torsionfit=true.

Input. The inline coordinates are the working geometry; the mol2 file supplies topology, atom types, and charges, and the single key is set in the sidecar. The coordinate block and the mol2 must list the same atoms in the same order, hydrogens included: MAPLE checks only that the atom counts match and then pairs atoms by position, so it cannot reconcile two files whose atom orders differ. The coordinate values themselves need not match the mol2. The header declares the route with method=refinement:

No typed mol2 at hand?

This tutorial ships choi001_gaff2.mol2, but mol2= is optional: omit it and ParmFit writes the inline coordinates to <base>_work/ante.pdb, types them with antechamber -at gaff2 into <base>_work/<base>_ff.mol2 (residue LIG), and fills the charge column with zero placeholders — chg_fit then defaults to abcg2, so the final charges still come from the charge stage rather than the placeholders.

Run. In the folder that holds Refine1.inp, Refine1.in, and choi001_gaff2.mol2:

maple Refine1.inp Refine1.out    # or simply: maple Refine1.inp

The second argument names the log; without it, MAPLE derives the log name from the input, so both forms write Refine1.out. The run also writes the resolved configuration Refine1.parmfitrun.in and the work directory Refine1_work/. A run has finished normally when the result block reads Status: completed and the log ends with a TOTAL RUN TIME line; on the tutorial hardware Case 1 takes about 22 s.

What happens.

  1. Initial parameters. parmchk2 -s gaff2 -a Y builds Refine1_work/Refine1_original.frcmod from the input mol2.
  2. Optimization. The MLIP (machine-learned interatomic potential; LBFGS) relaxes the inline coordinates.
  3. Bonded refinement. An MLIP Cartesian Hessian feeds mSeminario, which updates the bonded terms — including the GAFF2 i-ca bond to the iodine, whose force constant is revised substantially (see the table below).
  4. Charges. With chg_fit=none, the charges of the input mol2 are kept unchanged; no chargefit/ directory is created.
  5. TorsionFit. Auto-selection finds exactly one rotatable torsion — the exocyclic phenol C–O bond (11, 12), whose rotation swings the hydroxyl over the ortho-iodine; ring torsions are excluded. This bond is scanned a full circle every 10° by default and fitted in two stages.
  6. Export. Amber mol2/frcmod/tleap input and GROMACS top/gro files are written.

The resolved configuration. Next to Refine1.out, MAPLE writes Refine1.parmfitrun.in. For this case almost every entry is a filled-in default:

Case 2 — RESP charges and a QM geometry

What changed. The sidecar gains four keys. With chg_fit=resp, charges are derived at runtime — Gaussian evaluates the ESP (electrostatic potential), then AmberTools performs the two-stage RESP fit. With iqm=true and opt_level=B3LYP/def2SVP, the geometry and Hessian references move to Gaussian. With the default qm_mode=1, the torsion scan stays MLIP-driven, with a QM single point at each frame.

One level choice is iodine-specific: the classic RESP basis HF/6-31G(d) does not exist for iodine, so this case sets chg_level=HF/def2SVP — the def2 family carries iodine with its effective core potential. Note also the level spelling: with qm_engine=g16, write B3LYP/def2SVP without the hyphen — the engine-spelling rule is documented in the hub's Levels of Theory.

Run. maple Refine2.inp Refine2.out, as in Case 1; on the tutorial hardware it takes about 7 min, and Refine2.parmfitrun.in shows the four new keys resolved against their defaults.

What happens. The MLIP pre-optimization still runs, then a QM opt+frequency job supersedes it as the reference geometry and Hessian source for mSeminario. Charge derivation runs regardless of the iqm setting — Gaussian supplies the ESP, AmberTools performs the RESP stages; the Gaussian jobs run with the configured qm_nproc/qm_mem.

The iodine radius detail. Open Refine2_work/chargefit/resp.gjf and the route line is not the plain Pop=MK you may know from light molecules:

#P HF/def2SVP Pop(MK,ReadRadii) IOp(6/33=2) SCF=Tight

... (molecule specification)

I 1.875

Gaussian's built-in Merz–Kollman radius table stops well before the fifth row, and l602 aborts with GetVDW: no radius for atomic number 53 otherwise. ParmFit therefore writes Pop(MK,ReadRadii) and appends a radius line for every element the built-in table lacks — 1.875 Å for iodine, from its UFF van der Waals radius divided by 1.2. Light molecules never need this fallback; without it, a molecule containing iodine cannot run.

Case 3 — Relaxing each frame on the QM surface

What changed. The configuration lives in the external sidecar files referenced with input= — the method itself stays in the inline #parmfit(...) header. Case 2 kept the default qm_mode=1, in which QM single-points score the MLIP scan’s frames; this case makes the choice explicit, running Refinement with qm_mode=2 and qm_mode=3. The Refine4 header declares level=tight: mode 3 hands the frame relaxation to ParmFit’s own optimizer, and level is MAPLE’s global convergence tier, so the run raises that optimizer’s stopping criteria from the default medium tier to tight — the same depth g16’s own optimizer stops at.

Run. maple Refine3.inp Refine3.out and maple Refine4.inp Refine4.out, as in Case 1; on the tutorial hardware they take about 28 min and 1 h 36 min, and their resolved configurations Refine3.parmfitrun.in and Refine4.parmfitrun.in differ only in qm_mode, 2 versus 3.

What happens. The charge and reference setup is identical to Case 2; only the way QM data enters TorsionFit changes. In mode 2, each scan frame comes from a QM constrained optimization of the torsion; in mode 3, the QM engine evaluates energies and forces directly and MAPLE's own optimizer drives the scan — see the hub's qm_mode table for the full semantics. The header and stage line always report the active mode — here from Refine3.out:

QM reference:     enabled, mode=2, engine=g16, opt=B3LYP/def2SVP, sp=B3LYP/def2SVP
[Refinement] Using QM reference data for TorsionFit (mode=2) ...

The same B3LYP potential-energy surface and the same frozen dihedral underlie all three references — what differs is who relaxes each frame and where the relaxation stops. The rotor couples to the framework — the C–O bond breathes with conjugation, and the framework angles and the I···O contact absorb the steric load of the hydroxyl swinging past the iodine — so relaxed and unrelaxed frames are genuinely different geometries. Mode 1 scores the MLIP scan’s geometries as they are; modes 2 and 3 relax every frame on the QM surface, and with mode 3’s depth set by level=tight the two relaxed scans stop at the same depth. That is why the three profiles in Fig. 3 differ, and depth is what separates the run times in the table above.

The Gaussian-output totals in the table are job counts, not gradient-evaluation counts: mode 2 submits one Opt=ModRedundant constrained optimization per frame, while mode 3 submits one Force evaluation at a time as ParmFit’s optimizer steps from frame to frame — the tighter the level, the more evaluations.

Checkpoint

Pick the mode by what stands behind the reference and what it costs: mode 1 reuses the MLIP scan at single-point cost, mode 2 replaces each frame with a complete constrained QM optimization, mode 3 hands the scan steps to QM at single-force cost — raise its depth with level=tight as here, or accept the default medium tier and its shallower frames. Every product path above is relative to the run’s <base>_work/ directory.
